# Copy and Translations

Read this guide before adding or changing user-facing text.

## Language selection

`I18nProvider` (`src/shared/i18n/i18n.tsx`) holds the language (`zh` or `en`). It reads a `lang` query parameter first, then the `ffe-language` value in `localStorage`, then the browser language (English when it starts with `en`), and defaults to Chinese. It keeps `<html lang>` and `data-language` in sync.

## Writing copy in components

Source copy is Chinese. Components translate it in one of two ways:

- `t("中文文案 {name}", { name })` looks the Chinese text up in the translation tables. Use it for shared or repeated copy. Placeholders in braces are filled from the variables.
- `useText()` returns `text("中文", "English")` for one-off copy written inline as a pair.

Every new string needs an English version: either an entry in `zhToEn` in `src/shared/i18n/translations.ts` or an inline pair. Untranslated `t()` text falls back to the Chinese source, which is a visible bug in English mode. English copy is usually longer; check layouts in both languages.

## Translation tables

- `zhToEn` in `translations.ts` is the hand-maintained table and wins over the generated one.
- `translations-generated.json` is a large Chinese-to-English table that was generated outside the repository; no generator is checked in. Treat it as data: correct a wrong entry by adding an override to `zhToEn`.
- `translateToZh` reverses both tables for English text produced by models.

## Server and model output

API routes read `lang` from the request and choose copy with `pick(language, zh, en)` or `localized(...)`. Recognition prompts ask the model for text in the request language; only the legacy `FOOD_ROUTER=llm` mode also asks for `*Zh`/`*En` mirror fields. `getLocalizedFoodField` reads mirror fields when present and otherwise translates through the tables, so saved foods display in either language.
